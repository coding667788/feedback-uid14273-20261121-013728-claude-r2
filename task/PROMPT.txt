为隔离环境写一套通信加密配置通告审计器。六种以内的合成套件各有强度整数。一次逻辑握手由发起方提供有序套件、接收方采用自己的有序列表选第一个共同项；失败没有回退。端点角色不同导致两方向结果可不同。每个节点分属一个升级批次，批次内端点同时变更，由有向依赖图限制批次先后。通信要求按有向端点对给出最低强度及是否允许临时断开；禁止的套件即使强度够也不得协商。列出升级前后端点配置，并给定固定的不可更改通信要求。
audit 按指定批次顺序逐阶段（含初始、最终）计算协商矩阵和每条要求的失败原因。plan 在所有合法顺序中找始终满足硬约束的方案，再最小化临时断开的「阶段数乘该连接的权重」总和，最后取字典序最小批次序列；不能完成时输出可达的最大升级数量、同样按字典序取路径，以及该状态全部依赖已满足的下一步分别违反哪条硬约束。规划中阶段只与已升级集合有关，支持 18 个批次，禁止逐个枚举所有完整排列。测试覆盖强套件存在却被优先级较高的弱项盖住、反向结果变化、只有一种顺序可行、局部低损失不保证全局最优和无解路径可回放。仅做配置模型，使用虚构节点与套件。

升级批次具有正整数持续时间和允许开始的时刻集合，全局最多允许两个批次处于执行中。每批开始时该批端点暂时离线，完成时这些端点同时改用新配置并恢复。若一批依赖另一批，必须等依赖完成。每个整秒先处理全部完成事件，再开始允许的新批次，然后审查到下个整秒的状态；任一开始时刻上同批开始集合本身也必须合法。加入冗余通信业务：一项业务列多个可替代的有向端点对，只要在每个虚构单故障域失效情景中仍有至少一个允许、强度够的端点对就合规。同一批相关端点和站点可以共享故障域，安全下限仍在每条可协商的端点对上分别判定，备份可用不能掩盖弱协商。在给定终止时刻前规划所有批次的开始时刻，依次最小化可暂断连接的按秒加权中断、全部完成时刻及按 (开始秒,批次 ID) 排序的计划；返回逐阶段所有故障情景的见证。原题中的指定顺序等价于依次完成后才开启下一批，仍可审计。测试要有允许两批重叠时才满足截止、平时可用但同一故障域下双路一起失效、同秒完工和开工的原子边界、暂时离线时误读新配置，以及已升级集合相同但在途剩余时间不同导致一个状态不能被另一个合并。调度场景支持 14 个批次、64 秒。

使用 Windows 原生 Python 3.12、标准库和 CPU，从空仓库实现，所有夹具用本地虚构数据。命令格式为 python -m solution <命令> CASE.json，涉及持久状态的命令带 --db DB.sqlite。标准输出为 UTF-8 JSON，同一逻辑输入产生同一结果；结构错误给出可定位的错误码及字段位置。交付可直接运行的样例、README（含完整输入输出定义与复现命令）和可用 python -m unittest discover -s tests -v 执行的断言测试。
